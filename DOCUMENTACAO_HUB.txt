1. VISÃO GERAL DO PRODUTO
================================================================================
O HUB é uma plataforma web interna que centraliza:

 • Gestão de PROJETOS (clientes) e seus vínculos com INVESTIDORES (colaboradores).
 • Cálculo de REMUNERAÇÃO VARIÁVEL mensal baseada em performance:
     - MRR trabalhado (entregue) vs. MRR total da carteira
     - Churn
     - Flags de performance (GREEN / YELLOW) e streaks
 • Controle de ENTREGAS mensais por cargo:
     - Operação (Account / Gestor de Tráfego / Cientista)
     - Criativa (Designer / WebDesigner)
 • Painel de OPERAÇÃO por cliente: plano de mídia, otimizações, check-ins
   semanais, relatórios, KPIs, forecasting, links úteis e tarefas.
 • KANBAN configurável de fluxo de projetos (fases → status do projeto).
 • AUTOMAÇÕES disparadas por eventos do Kanban ou por datas do projeto
   (ação = webhook, ex.: Google Chat).
 • RANKING de performance dos colaboradores.
 • Login por e-mail/senha, Google OAuth e BIOMETRIA FACIAL.

Público: colaboradores da agência, organizados por SQUAD, com CARGOS (funcao)
e POSIÇÕES hierárquicas (Sócio, Gerência, Coordenador, etc.).

4. CONFIGURAÇÃO E VARIÁVEIS DE AMBIENTE (.env)
================================================================================
O arquivo .env (carregado por python-dotenv) deve conter:

  # Banco de dados PostgreSQL
  DB_HOST=...
  DB_PORT=5432
  DB_DATABASE=...
  DB_USERNAME=...
  DB_PASSWORD=...

  # Flask
  SECRET_KEY=...            # chave de sessão (fallback: os.urandom se ausente)

  # Google OAuth (login com Google)
  GOOGLE_CLIENT_ID=...
  GOOGLE_CLIENT_SECRET=...
  REDIRECT_URI=...          # ex.: https://seu-dominio/login/callback

  # Biometria facial (opcional)
  FACE_MATCH_THRESHOLD=0.75 # similaridade mínima para aceitar o rosto

A connection string é montada em database.py:
  postgresql+psycopg2://{DB_USERNAME}:{DB_PASSWORD}@{DB_HOST}:{DB_PORT}/{DB_DATABASE}

Pool de conexões: pool_pre_ping=True, pool_recycle=300s (recicla a cada 5 min).
Sessão Flask: dura 7 dias (permanent_session_lifetime).

6.6 investidores_metricas_mensais_novo  (MÉTRICA MENSAL por colaborador)
------------------------------------------------------------------------------
  Chave composta: email_investidor + mes + ano
  ativo, detalhes (JSONB), cargo, senioridade, level, flag, motivo_flag,
  green_streak, yellow_streak,
  fixo_mrr_atual, fixo_mrr_entrega, fixo_churn_atual, fixo_remuneracao_fixa,
  fixo_csp_esperado, fixo_churn_maximo_percentual, fixo_mrr_minimo,
  fixo_mrr_esperado, fixo_mrr_teto, fixo_churn_maximo_valor,
  fixo_remuneracao_minima, fixo_remuneracao_maxima, fixo_mrr_projeto_total,
  historico_projetos (JSONB), entregas_criativos (JSONB),
  entregas_operacao (JSONB),
  -- Colunas GENERATED (calculadas pelo PostgreSQL, FetchedValue):
  calc_churn_real_percentual, calc_delta_churn_percentual,
  calc_delta_churn_valor, calc_variavel_churn, calc_delta_csp,
  calc_variavel_csp, calc_variavel_total, calc_remuneracao_total

  • É o "extrato" mensal de cada colaborador. As colunas calc_* são GENERATED
    ALWAYS AS STORED no banco — Python só grava as colunas fixo_*; o banco
    deriva as variáveis. (Por isso db.flush() individual em vez de bulk.)
  • Fórmulas (ver estrutura/Tabela_metricas_mensais.md):
      Churn Real %     = Churn Atual / MRR Atual
      Delta Churn %    = Churn Máximo % − Churn Real %
      Delta Churn $    = Delta Churn % × MRR Atual
      Variável Churn   = Delta Churn $ × CSP Esperado
      Delta CSP        = CSP Esperado − (Remuneração Fixa / MRR Atual)
      Variável CSP     = Delta CSP × MRR Atual
      Variável Total   = Variável CSP + Variável Churn
      Remuneração Total= Remuneração Fixa + Variável Total
  • IMPORTANTE: fixo_mrr_atual é o DENOMINADOR das colunas GENERATED. Gravar
    um valor proporcional baixo com churn alto pode estourar NUMERIC(8,7).
    Por isso a sincronização proporcional grava só fixo_mrr_projeto_total.

7. AUTENTICAÇÃO E CONTROLE DE ACESSO
================================================================================
7.1 Métodos de login
 a) E-mail + senha (POST /login): valida em investidores, checa ativo=True e
    check_password_hash; gera token (os.urandom) e faz upsert em auth; popula
    a sessão Flask (nome, email, token, funcao, posicao, senioridade, squad,
    nivel_acesso, pode_editar_kanban, profile_picture).
 b) Google OAuth (/login/google → /login/callback): autentica via Google,
    busca o e-mail em investidores (precisa existir e estar ativo), cria token
    e sessão. Usa requests-oauthlib (scopes: email, profile).
 c) Biometria facial (/api/face/login/*): ver seção 17.
 d) /dev-login: atalho de desenvolvimento (usuário fixo).

7.2 Decorators de proteção
 • @check_session  → exige "nome" na sessão; senão redireciona para /login.
 • @check_access(roles) → exige que session["funcao"] esteja em `roles`,
   OU que session["posicao"] seja de alto nível (Gerência / Sócio /
   Coordenador). Normaliza Unicode (NFC) para comparar cargos com acento.
   Acesso negado → renderiza index.html com error="Acesso restrito.".

7.3 Hierarquia de visibilidade (padrão recorrente nas telas)
 • Admin / Sócio / Gerência → enxergam TUDO (acesso global).
 • Coordenador             → enxerga apenas a própria SQUAD.
 • Demais cargos           → enxergam apenas a si mesmos / seus vínculos.

7.4 Senha
 • Hash com werkzeug (generate_password_hash / check_password_hash).
 • Troca via POST /alterar-senha (valida senha atual + confirmação).
 • Reset administrativo via POST /api/admin/usuarios/reset-password.

8. CONCEITOS CENTRAIS DE NEGÓCIO
================================================================================
8.1 MRR Total vs. MRR Trabalhado (Entregue)
 • MRR Total (fixo_mrr_projeto_total): soma dos FEES BRUTOS de todos os
   projetos ativos vinculados ao colaborador. É o potencial máximo da carteira.
 • MRR Trabalhado / Entregue (fixo_mrr_entrega / fixo_mrr_atual): valor que o
   colaborador efetivamente "ganhou", proporcional ao cumprimento das entregas
   de cada projeto. É a base da remuneração variável.

8.2 Proporcionalidade por dias
 • Quando um vínculo entra/sai no meio do mês, o fee é proporcional aos dias:
       valor_proporcional = (dias_trabalhados × fee) / dias_no_mês
 • Calculado em ProjetoParticipacaoService.calcular_valor_proporcional.

8.3 Cientista (multiplicador 1.5x)
 • Vínculo com cientista=True recebe fee × 1.5.
 • O período de cientista pode ser parcial (cientista_entrada/saida no metadata
   extra do projeto). O cálculo separa: dias como cientista (1.5x) + dias como
   investidor puro (1.0x), via interseção de intervalos.

8.4 As 4 entregas (milestones) — cada uma vale 25%
 • OPERAÇÃO (Account/GT): conjunto de entregas por cargo (ver 8.5).
 • CRIATIVA (Designer): criativos + vídeos + LP (contratados vs. entregues).
 • progresso_projeto = entregues / contratados (com cap por categoria).
 • Contribuição do projeto ao MRR = fee_proporcional × progresso_projeto.

8.5 Entregas por cargo (templates)
 ACCOUNT (_ENTREGAS_ACCOUNT_TPL):
   relatorio_account (meta 1), planner_monday (meta 4), csat_checkin (meta 4),
   forecasting (meta 1)
 GESTOR DE TRÁFEGO (_ENTREGAS_GT_TPL):
   kpis (1), plano_de_midia (1), documento_de_otimizacao (4), relatorio_gt (1)
 CIENTISTA: união de Account + GT, com relatórios unificados em
   "relatorio_mensal".

8.6 Flags de performance (GREEN / YELLOW)
 Avaliadas sobre o MRR DO PORTFÓLIO (mrr_portfolio_total) e o churn:
   • GREEN  → churn ≤ churn_máximo E mrr_mínimo ≤ portfolio ≤ mrr_teto.
   • GREEN PDC (direto) → ultrapassou o teto de MRR com churn OK
     (garante streak mínimo de 3).
   • YELLOW → caso contrário (motivo_flag detalha o porquê).
   • Sócio sem cargo operacional → GREEN automático.

8.7 Streaks
 • green_streak / yellow_streak contam meses CONSECUTIVOS na mesma flag.
 • Mês anterior precisa ser imediatamente consecutivo; senão reinicia.

8.8 Faturamento variável
 • Projetos com extra.contrato_variavel=True somam um valor variável
   (% sobre faturamento do cliente) ao MRR — somado DEPOIS do multiplicador
   cientista: resultado = (fee × 1.5) + valor_variavel.

8.9 Regras temporais especiais (hardcoded)
 • Meses 02/2026 e 03/2026: progresso = 0 para todos (nenhuma entrega contada).
 • Baseline de início para população inicial: 01/03/2026.
 • Sincronização/recalculo só ocorre para o mês CORRENTE ou futuro — meses
   fechados (anteriores) são protegidos contra recálculo.

9. MÓDULO REMUNERAÇÃO — services/remuneracao.py
================================================================================
Função principal: calcular_metricas_mensais(mes, ano)

Fluxo:
 0. Bulk UPDATE: sincroniza MetricaMensal.ativo com Investidor.ativo.
 1. Busca investidores ATIVOS com funcao preenchida.
 2. Indexa remuneracao_cargos por (cargo, senioridade, level).
 3. Para cada investidor:
    • Carrega a MetricaMensal do mês (e historico_projetos).
    • Soma o MRR do portfólio (fees completos dos vínculos ativos), converte
      USD→BRL, aplica cientista 1.5x.
    • Calcula churn proporcional dos vínculos inativados NO MÊS corrente.
    • Determina a Flag (GREEN/YELLOW), motivo e streaks.
    • Calcula o MRR ENTREGUE por projeto:
        progresso × fee_proporcional, somando todos os projetos.
        - Criativo: (criativos+videos+lp) entregues/contratados, cap por categoria.
        - Operação: soma metas vs. entregues do checklist.
        - Meses 02/03 de 2026 → progresso 0.
    • Grava fixo_mrr_atual = fixo_mrr_entrega = novo_mrr; demais fixo_* do cargo.
    • db.flush() individual (por causa das colunas GENERATED).
 4. db.commit().
 5. Pós-processamento: aplica faturamento variável (idempotente).

Recálculo é exposto por:
 • GET  /api/remuneracao/processar
 • GET  /api/remuneracao/recalcular-historico
 • POST /api/remuneracao/recalcular-investidor/<email>/<mes>/<ano>
 • Job diário (00:00) — ver seção 19.

17. BIOMETRIA FACIAL — face_auth/face_service.py
================================================================================
Login e cadastro por reconhecimento facial usando insightface (modelo buffalo_l,
embeddings de 512 dimensões), carregado lazily (CPUExecutionProvider).

Pipeline:
 • decode_frame(base64) → OpenCV frame.
 • detect_and_extract(frame) → embedding normalizado + bbox + (opcional)
   landmarks/head_pose/det_score.
 • process_frames_for_biometric_registration(frames) → média de embeddings
   (mín. 3 rostos detectados) → vetor de 512 salvo em user_faces.embedding.
 • compare_embeddings / match_face → cosine similarity ≥ FACE_MATCH_THRESHOLD
   (default 0.75) determina o match.

Liveness (anti-spoofing, helpers disponíveis):
 • validate_blink (EAR — eye aspect ratio < 0.18)
 • check_liveness_movement (deslocamento médio do bbox)
 • check_liveness_head_pose (variação de yaw)

APIs Face:
  GET  /api/face/biometry/status      POST /api/face/biometry/register
  POST /api/face/biometry/update      POST /api/face/biometry/delete
  POST /api/face/login/check          POST /api/face/login/authenticate
  POST /api/face/login/capture-and-auth
Todas as tentativas são auditadas em face_auth_log (status, similarity, IP, UA).

24. OBSERVAÇÕES, REGRAS ESPECIAIS E DÍVIDAS TÉCNICAS
================================================================================
Pontos de atenção para manutenção:

 1. COLUNAS GENERATED — investidores_metricas_mensais_novo tem colunas calc_*
    derivadas pelo Postgres. Nunca tente gravá-las pelo ORM. Use db.flush()
    individual (não bulk) ao salvar métricas, pois o bulk quebra com FetchedValue.

 2. fixo_mrr_atual É DENOMINADOR — gravar valores baixos com churn alto estoura
    NUMERIC(8,7) (calc_churn_real_percentual etc.). A sincronização proporcional
    propositalmente NÃO grava fixo_mrr_atual.

 3. DUAS IMPLEMENTAÇÕES DE ENTREGA convivem:
    (a) remuneracao.py usando entregas_operacao/entregas_criativos (JSONB na
        MetricaMensal) — fonte canônica do MRR exibido.
    (b) delivery_engine.py usando a tabela monthly_deliveries.
    Ao evoluir, alinhar/qual é a oficial para evitar divergência.

 4. AUTO-SYNC SÓ SOBE (max) — operacao_service.sync_to_metrica nunca derruba o
    que o usuário marcou manualmente em /criativa. Cuidado ao alterar essa regra.

 5. REGRAS TEMPORAIS HARDCODED — meses 02/2026 e 03/2026 zerados; baseline
    01/03/2026. Revisar antes de virar o ano/competência.

 6. MESES FECHADOS são protegidos contra recálculo (mês < corrente). Recalcular
    histórico exige rotas específicas.

 7. /dev-login e /api/operacao/test-db são utilitários de desenvolvimento —
    avaliar remoção/proteção em produção.

 8. SQL PURO na tabela "operacao" e em faturamento_variavel — não há model ORM;
    alterações de schema precisam ser manuais e refletidas nas queries text().

 9. error_log_home1.txt / error_log_home2.txt — a home grava tracebacks em
    arquivo quando falha ao montar o dashboard (debug). Limpar em produção.

10. scratch/ e migrations soltas na raiz poluem o repositório — recomendado
    mover para uma pasta arquivada e manter só o que é runtime.

11. SEGREDOS — manter .env fora do versionamento (já no .gitignore). Conferir
    que GOOGLE_CLIENT_SECRET / DB_PASSWORD não estão commitados.
